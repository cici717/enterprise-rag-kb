## 简历详细版

**项目背景**

企业知识分散在制度文档、产品手册和 FAQ 中，员工查找信息效率低。传统搜索只能返回文档链接，无法直接回答问题；直接使用大模型又容易产生幻觉。因此使用 RAG 方案，让模型基于检索到的企业资料回答，并返回引用来源。

**主要工作**

1. 设计后端分层结构，将配置、数据库、文档处理、检索、LLM 调用和接口层解耦。
2. 实现文档解析流程，支持 PDF、Word、TXT 和 Markdown，并按段落和句子进行切分。
3. 实现 EmbeddingProvider 抽象，支持离线哈希向量和 OpenAI 兼容 Embedding 接口。
4. 实现向量检索和关键词检索融合，按综合分数返回 Top-K 片段。
5. 设计引用溯源结构，每个片段保存文档 ID、文件名、页码、片段序号和相关度。
6. 接入 DeepSeek、Qwen、GLM、OpenAI 等 OpenAI 兼容接口，支持普通回答和 SSE 流式回答。
7. 使用 SQLite 保存文档、Chunk、会话、消息和反馈，提供文档管理、会话查询和反馈接口。
8. 使用 Streamlit 实现上传、文档列表、检索片段数调节和流式聊天界面。
9. 使用 pytest 编写单元测试，并提供示例文档导入和检索评测脚本。
10. 提供 Dockerfile 和 Docker Compose 配置，支持本地和容器化部署。

**项目结果**

- 示例数据共有 2 个文档，评测问题 5 个，检索命中 5 个。
- 完成文档上传、向量检索、引用返回、流式输出和会话历史完整链路验证。
- 项目默认无 API Key 也能运行，降低演示门槛；配置 API Key 后可切换真实大模型回答。

## 一分钟口述版

我做了一个企业知识库 RAG 智能问答平台。用户上传公司制度、产品手册等文档后，系统会先解析和切分文档，再生成向量索引。用户提问时，系统先做向量和关键词混合检索，把最相关的片段交给大模型，回答时返回引用来源。后端使用 FastAPI 和 SQLAlchemy，前端使用 Streamlit，支持流式输出和会话历史。这个项目重点解决的是大模型幻觉和回答不可追溯的问题。我还写了单元测试和评测脚本，示例问题检索命中率是 5/5。
