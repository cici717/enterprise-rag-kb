# 企业知识库 RAG 项目面试讲稿

## 1. 项目一句话介绍

这是一个基于 RAG 的企业知识库问答系统。用户上传 PDF、Word、TXT 或 Markdown 文档，系统完成解析、切分、向量化，用户提问时先检索相关片段，再让大模型基于片段生成带引用的回答。

## 2. 技术选型

- FastAPI：接口开发，自带 OpenAPI 文档，适合快速构建 AI 应用后端。
- SQLAlchemy：管理文档、Chunk、会话、消息和反馈数据。
- SQLite：个人项目和本地演示部署成本低。
- Streamlit：快速完成可演示的前端。
- OpenAI 兼容接口：可以接 DeepSeek、Qwen、GLM、OpenAI。
- SSE：实现逐字流式输出，前端体验更自然。
- pytest：验证切分、Embedding、相似度计算等核心逻辑。

## 3. 核心流程

1. 上传文档。
2. 根据文件类型选择解析器，PDF 使用 pypdf，Word 使用 python-docx，文本直接读取。
3. 按段落和句子切分 Chunk，默认 800 字符，重叠 120 字符。
4. 对每个 Chunk 生成 Embedding。
5. 将 Chunk 内容、引用信息和向量保存到数据库。
6. 用户提问时，对问题生成 Embedding。
7. 计算问题和每个 Chunk 的向量相似度，同时计算关键词重合度。
8. 按综合分数排序，取 Top-K。
9. 将 Top-K 片段拼进 Prompt，要求模型只根据资料回答。
10. 通过 SSE 返回模型回答，同时返回引用来源。
11. 保存用户消息、助手消息和引用信息。

## 4. 高频面试问题

### Q1：为什么用 RAG，不直接微调模型？

微调适合改变模型风格或提升特定任务能力，但企业知识更新频繁，微调成本高，更新知识还需要重新训练。RAG 把知识放在外部文档库中，更新文档后重新建立索引即可，成本低，而且可以返回引用来源，方便排查和信任。

### Q2：文档为什么要切分？

大模型上下文有限，整篇文档直接输入成本高、噪声大，检索效果也不好。切分成 Chunk 后，可以只把最相关的片段放进 Prompt，提高准确率并降低 Token 消耗。

### Q3：Chunk 大小怎么确定？

没有固定标准，需要根据文档类型和模型上下文实验。我的项目默认 800 字符，重叠 120 字符。制度类文档按章节和段落切分效果较好；技术文档可以按标题层级切分。实际项目中会准备评测集，对比不同 Chunk 大小对召回率和回答准确率的影响。

### Q4：为什么做混合检索？

单纯向量检索擅长语义相似，但对订单号、专有名词、精确关键词不一定稳定。关键词检索对精确匹配更敏感。两者融合可以兼顾语义召回和精确匹配，提高整体稳定性。

### Q5：怎么减少幻觉？

第一，Prompt 明确要求只能根据资料回答，资料不足就说不知道。第二，回答附带引用来源。第三，检索 Top-K 片段作为唯一上下文。第四，后续可以加入 Rerank、答案忠实度评测和人工反馈。

### Q6：引用溯源怎么实现？

每个 Chunk 在入库时保存 document_id、filename、page、chunk_index 和内容片段。检索结果返回这些元数据，前端在回答下方显示引用来源。这样用户可以回到原文档核对。

### Q7：流式输出怎么实现？

后端使用 SSE，返回 `data: {...}` 格式的事件。先发送会话 ID 和引用信息，再逐个 token 发送模型输出，最后发送 done 事件。前端使用 httpx 持续读取响应，每收到一个 token 就更新界面。

### Q8：为什么现在用 SQLite 向量检索，不用 Chroma？

当前实现适合个人项目和中小规模知识库，优点是部署简单、没有额外服务依赖，也能完整展示 RAG 流程。生产环境数据量增大后，我会把检索层替换成 Chroma、Milvus 或 pgvector，并使用 HNSW 等索引；接口层不需要大改。

### Q9：项目怎么评估？

我写了评测脚本，准备问题和预期关键词，调用问答接口后检查回答或引用中是否包含预期内容。当前示例数据是 5 个问题，命中 5 个。更完整的评估还会统计 Recall@K、答案忠实度、引用准确率和响应时间。

### Q10：如果文档量很大，性能怎么优化？

第一，使用专业向量数据库和 ANN 索引。第二，文档入库异步化，使用 Celery 或 RQ。第三，增加缓存。第四，使用 Rerank 只对 Top-N 结果精排。第五，按部门和权限过滤候选文档，减少检索范围。

### Q11：如何做权限控制？

可以在文档表增加 owner_department 和 visibility 字段，在检索前根据当前用户部门过滤 Chunk。权限校验放在检索层，不能只放在前端，否则用户可能通过接口访问无权限文档。

### Q12：API Key 怎么保护？

API Key 放在 `.env` 中，不写进代码，不提交到 Git。线上部署使用环境变量或密钥管理服务。日志中不能打印 Key。前端不能直接持有大模型 Key，所有模型调用都通过后端完成。

## 5. 项目难点与解决

### 难点一：检索结果不稳定

解决：使用向量相似度和关键词分数融合，并保留 Top-K 结果。后续可以接 Rerank 模型。

### 难点二：回答不可追溯

解决：Chunk 入库时记录文档、页码和片段序号，检索结果一并返回，前端展示引用来源。

### 难点三：没有 API Key 无法演示

解决：设计 MockLLM 和离线 Embedding 兜底模式。没有 Key 时仍能展示完整检索、引用和流式输出流程，配置 Key 后切换真实模型。

### 难点四：流式输出和会话保存冲突

解决：流式接口单独创建数据库 Session，在发送完 token 后统一保存用户消息和助手消息，避免依赖请求生命周期中的 Session。
